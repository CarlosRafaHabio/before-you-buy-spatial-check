# Persistence boundary — design contract

Status: design-only hardening note for engine 0.3.0. This document does not add
persistence to the core and does not change the public API.

## Purpose

The current lifecycle authority is deliberately process-local. A
`LifecycleRegistry` can reject stale revisions and revoked receipts only while that
exact live registry exists. Restarting the process creates a new authority, so old
claims may be reviewed and admitted again. This is a documented V0 limitation, not a
persistence bug in the geometry engine.

Hosts that need continuity across restarts must add a durable authority layer outside
the deterministic core. That layer must preserve lifecycle facts without treating
stored JSON, digests or identifiers as self-authenticating evidence.

## Ownership boundary

The deterministic core owns:

- validation of the current in-process opaque receipt;
- immutable claim/content checks within a live authority;
- revision replacement and revocation within that authority;
- fail-closed evaluation when admission is absent, stale or revoked;
- deterministic geometry for the admitted snapshot.

A durable host or adapter owns:

- creation of a durable authority identity;
- persistence of case/revision lifecycle state;
- persistence of external review events and canonical reviewed payloads;
- ordering/serialization of lifecycle mutations for one case;
- restart recovery;
- replay policy across process lifetimes;
- transport/storage integrity and authentication appropriate to its threat model.

The core must not infer durable authority from a user/model supplied
`authority_instance_id`, `case_id`, revision label, digest, report or receipt ID.

## Minimum durable state

A host that claims lifecycle continuity across restart should retain at least:

1. an authority identity generated by trusted host bootstrap;
2. the stable case identity selected by the host;
3. every seen revision label for that case, including superseded and revoked history;
4. the canonical reviewed evidence payload and its digest for each admitted revision;
5. the independently captured review/confirmation event reference;
6. current lifecycle state: current revision or revoked/no-current;
7. a monotonic case sequence or equivalent serialization token;
8. enough audit context to distinguish separate authority instances and process runs.

Opaque in-process receipts are not durable state. They must never be serialized and
restored. After restart, the host reconstructs policy state, performs any required
fresh review under its product rules, and requests a new process-local admission.

## Restart contract

A restart creates a new in-process `LifecycleRegistry`. The durable host may use its
stored lifecycle record to decide which candidate revision is eligible for a new
review/admission, but it must not recreate or deserialize an old receipt.

For a previously current revision, the host must choose and document one policy:

- **fresh-review policy**: every restart requires a new external review event before
  re-admission; or
- **durable-review policy**: a prior review event may remain acceptable if the host
  can verify the retained canonical payload, lifecycle state, authority identity and
  integrity of the durable record.

The core does not select between these policies and neither policy authenticates
real-world measurements by itself.

## Replay and revision rules

A durable adapter claiming replay resistance should enforce all of the following:

- a superseded revision cannot become current again merely because a process restarted;
- a revoked case/revision cannot be re-admitted under the same lifecycle identity;
- changed content under an already-seen `(case_id, revision)` is rejected;
- an unseen new revision may become current only after the host's required review;
- stale reports and exported JSON remain historical and never restore admission;
- receipt IDs, domain IDs, digests and confirmation references are not credentials;
- a model-provided lifecycle label never creates, selects or advances authority state.

If a product intentionally allows a revoked or superseded snapshot to be reconsidered,
it must create a new host-controlled revision and review event rather than resurrecting
the old lifecycle entry.

## Concurrency contract

V0 assumes ordered operations per case. A persistent adapter that introduces multiple
workers must provide serialization or compare-and-swap semantics for lifecycle writes.
At minimum, two workers must not both advance the same case from the same prior state
without one observing a conflict.

The persistence layer must therefore expose an atomic state transition equivalent to:

`expected_case_sequence -> next_case_sequence + lifecycle mutation`

A last-write-wins database update is insufficient for a host claiming revision or
revocation continuity.

## Integrity and provenance

Persistence changes availability of lifecycle history; it does not create provenance.

A host that transports durable lifecycle records across trust domains must add its own
integrity/authentication mechanism. The engine deliberately does not prescribe keys,
signatures, identity providers or remote attestation.

A SHA-256 digest can detect accidental/content mismatch against a known canonical
record. It does not prove who supplied the record or that the record is current.

## Failure rules

On durable-store read/write failure, ambiguity or concurrency conflict:

- do not manufacture a current receipt;
- do not fall back to the last favorable engine result;
- do not silently create a fresh independent authority to continue;
- block authoritative current presentation until lifecycle state is resolved;
- historical reports may still be shown only as historical, not live decisions.

## Adversarial test matrix

A persistent adapter should pass at least these scenarios before claiming durable
lifecycle continuity:

| ID | Scenario | Required result |
| --- | --- | --- |
| P01 | Restart after current admission | Old opaque receipt cannot be restored; policy controls any new admission |
| P02 | Restart after revocation | Same lifecycle revision remains ineligible |
| P03 | Restart after supersession | Superseded revision cannot become current again |
| P04 | Same case/revision, changed payload | Reject content substitution |
| P05 | Imported historical result JSON | Never creates current admission |
| P06 | Forged authority/domain/receipt IDs | Never reconstructs authority |
| P07 | Repeated confirmation_ref | Does not alias two emissions or lifecycle entries |
| P08 | Two workers advance same case concurrently | One transition conflicts or observes updated sequence |
| P09 | Durable store unavailable during mutation | Fail closed; no favorable fallback |
| P10 | Model supplies case/revision/authority labels | Labels remain data; host state controls identity |
| P11 | Old canonical payload replayed after newer revision | Reject resurrection under old revision |
| P12 | Revoked content submitted as unseen new revision | Requires the host's normal new-review policy; no automatic trust |
| P13 | Durable record tampered without valid integrity context | Host rejects before admission when integrity is part of its threat model |
| P14 | New process with no durable state available | Must not claim continuity with the previous authority |

These tests belong to a future adapter/host implementation. The current core tests
should continue demonstrating the opposite boundary: process-local lifecycle only.

## Non-goals for engine 0.3.x

This design note does not authorize:

- adding a database dependency to the core;
- serializing `LifecycleRegistry` or trusted receipts;
- adding authentication, sessions or user identity to the engine;
- making network calls from the engine;
- converting historical reports into live authority;
- changing geometry, evidence semantics or public result states.

Any implementation that changes those boundaries requires a separate design review,
tests and version decision.
